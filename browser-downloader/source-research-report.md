# Deep Research: Browser-downloader Sources vs. TikTok/Instagram Support

**Scope.** This report assesses every entry in `browser-downloader/sources.txt` against the actual
decision in `problem.md` (do not accept TikTok/Instagram URLs unless the product can deliver a
reliable result or a precise, honest failure) and the proposed browser-fallback idea in `idea.md`.

**Method.** I inspected the supplied local design and implementation, reviewed each linked project's
declared purpose, licence, maintenance status, and documentation, and cross-checked the important
platform/protocol claims with primary documentation. This is an architectural and due-diligence
review, not a claim that any public platform can be downloaded irrespective of its terms, access
controls, or DRM.

## Executive summary

The correct immediate product decision is **experimental, feature-flagged TikTok and Instagram
support**, with an explicit fallback state—not “supported” and not a blanket browser solution. The
existing `yt-dlp` path already has platform routing, per-platform format/extractor options, cookie
configuration, and error plumbing. `yt-dlp` continues to fix both TikTok and Instagram extractors
and officially supports browser-cookie input; this is the lowest-risk path to validate first.
[yt-dlp README](https://github.com/yt-dlp/yt-dlp/blob/master/README.md)
[yt-dlp changelog](https://github.com/yt-dlp/yt-dlp/blob/master/Changelog.md)

The current browser microservice is a useful **research prototype**, not a reliable universal
fallback. It detects direct media and manifests after navigation and has an honest DRM/anti-bot
error taxonomy, but it does not preserve the browser request context when handing a manifest to
Streamlink, does not robustly establish an authenticated browser session, and is not a general
MediaSource extractor. For the affected platforms, the browser should be a narrowly scoped,
sandboxed second experiment after a current `yt-dlp` + controlled-cookie smoke test—not the primary
production extractor.

The “low-footprint Rust headless browser in a VM” portion is not supported by the evidence. The
candidate Rust browsers/engines are either incomplete browser engines, automation wrappers around
Chromium, early projects, or have licences unsuitable for this service. A maintained Playwright
Chromium container is the least speculative choice. The “record playback at 100× and slow it down”
fallback should be **rejected**: capture and media clocks are not generally accelerated together,
audio cannot be recovered faithfully from a screencast, it increases cost and legal/policy risk, and
it cannot cross DRM.

## Decision and staged path

| Stage       | Product state                    | What must be true                                                                                                         | Exit condition                                                                          |
| ----------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 0           | **Experimental** (default off)   | Current `yt-dlp`; only operator-managed, consented cookie files; detailed failure code                                    | A reproducible public/authorised happy path for each platform outside local development |
| 1           | Experimental browser fallback    | Isolated Chromium service, network observation, request-context handoff, per-platform metrics                             | 30-day smoke matrix shows a defined success SLO and no security/policy blockers         |
| 2           | Supported                        | Stable success rate, monitored regressions, documented cookie/session lifecycle and support ownership                     | Product owner explicitly accepts ongoing maintenance                                    |
| Any failure | Blocked/unsupported for that job | Return `login_required`, `challenge_required`, `rate_limited`, `geo_restricted`, `drm_detected`, or `no_supported_stream` | Never silently present generic “failed” as support                                      |

Do **not** use cookie theft, residential-proxy evasion, TLS/fingerprint spoofing, reverse-proxying
third-party pages, or DRM circumvention. Cookies are highly sensitive credentials. `yt-dlp` itself
cautions that browser-cookie exports can include cookies for every site; use a dedicated controlled
profile, a platform-scoped Netscape-format file mounted read-only as a secret, a documented
rotation/revocation procedure, and only content the account is authorised to retrieve.
[yt-dlp FAQ](https://github.com/yt-dlp/yt-dlp/wiki/FAQ)

## What the code already proves—and does not

The repository already contains more groundwork than the issue suggests:

- `app/services/yt_dlp_service.py` classifies TikTok/Instagram, accepts a cookie file/browser
  profile, has platform format chains and extractor args, and logs whether cookie configuration is
  absent.
- `packages/browser-downloader/` has a Dockerfile, bounded concurrency, SSRF/output validation, CDP
  observation, a DOM/blob attempt, Streamlink/FFmpeg handoff, and structured error mapping into the
  worker.
- It is nevertheless disabled by default and its browser route bypasses `yt-dlp` for
  TikTok/Instagram. That makes a browser experiment the first route when enabled, contrary to the
  lower-risk evidence-first path above.

Specific gaps before enabling it:

1. **Authentication context is lost.** A detected `.m3u8`/`.mpd` URL is passed to Streamlink without
   the browser cookies, Referer, User-Agent, or request headers. Signed URLs often depend on
   precisely that context. `yt-dlp` documents the same-IP/cookie/header constraint.
   [yt-dlp FAQ](https://github.com/yt-dlp/yt-dlp/wiki/FAQ)
2. **The blob mechanism is insufficient for MSE.** `URL.createObjectURL(MediaSource)` is
   deliberately ignored and fetching a `blob:` URL retrieves a completed Blob only; it does not
   reconstruct `SourceBuffer.appendBuffer` fragments, separate DASH audio/video, or a live stream.
3. **Playback is brittle.** The service tries a few generic selectors; consent dialogs, login pages,
   autoplay rules, lazy-load scroll, and platform-specific player controls are not a reliable
   playback contract.
4. **No user/session model.** There is no secure per-operator cookie mount or browser storage-state
   lifecycle in the browser service. A shared browser context must never be used for different
   users' sessions.
5. **“Universal” is a false promise.** DRM is an intentional technical boundary: EME's
   `MediaKeySystemAccess` exposes the browser key-system interface; recording or network observation
   does not yield clear protected media.
   [MDN EME reference](https://developer.mozilla.org/en-US/docs/Web/API/MediaKeySystemAccess)

## Recommended architecture

```text
accepted URL
  -> platform capability registry (not validator allow-list)
  -> current yt-dlp, platform profile, optional controlled cookie secret
  -> success: normal storage
  -> stable classified failure:
       experimental platform + authorised test cohort only
         -> isolated Chromium context -> observe unencrypted direct/HLS/DASH request
         -> download with the captured URL + required allow-listed request context
         -> success OR a specific terminal reason
       otherwise -> clear unsupported/experimental response
```

The capability registry should model `supported | experimental | blocked`, authentication
requirement, last successful smoke date, and a user-facing message. Validation should no longer be
the source of truth for “supported.”

For the browser service, preserve only the non-circumvention pipeline: fresh context per job; no
shared user data; minimal request/header propagation to an allow-listed downloader; an output mount
limited to the job directory; strict URL/redirect SSRF controls; CPU/memory/time caps; and a
job-level audit record with no cookies or tokens. A full VM is not necessary to decide
viability—existing container isolation can be strengthened before adding gVisor/VM complexity.

## Contrarian views and risks

- A browser can outperform an extractor where the page legitimately obtains short-lived signed media
  URLs, but that is a **compatibility advantage**, not universality. It may make failure modes more
  expensive and less reproducible.
- Extensions can observe requests but are not omnipotent; Chrome documents permission limits and MV3
  restrictions on blocking request modification. This supports using sniffing as detection, not
  building a proxy/evasion stack.
  [Chrome webRequest docs](https://developer.chrome.com/docs/extensions/reference/api/webRequest)
- A captured media URL may require session cookies, Origin/Referer, or the same IP; blindly
  replaying arbitrary browser headers would create a credential-exfiltration surface. Keep the
  request context in the sandbox and pass only an explicit safe subset.
- HLS/DASH tooling cannot decrypt DRM merely because it sees a manifest. DRM detection should remain
  a terminal, no-retry outcome.
  [MDN EME reference](https://developer.mozilla.org/en-US/docs/Web/API/MediaKeySystemAccess)
- Browser projects with “undetected” branding are not evidence of reliability. They trade a visible
  dependency upgrade path for an adversarial compatibility race and do not establish that the app
  has permission to fetch content.

## Open questions and validation matrix

1. Which public or operator-authorised TikTok and Instagram URLs can be used as durable smoke
   fixtures without retaining personal/session data?
2. Does the installed `yt-dlp` version reproduce the reported failure, with the exact classified
   stderr retained? Upgrade before diagnosing extractor drift.
3. For each fixture, does a dedicated controlled profile materially change the result? If yes, is
   the security and maintenance burden acceptable?
4. Does Chromium observe an unencrypted direct/HLS/DASH request after a minimal, platform-specific
   play action? If it does, can the download succeed when using only the permitted request context?
5. What success threshold and on-call ownership justify changing a platform from experimental to
   supported?

Minimum smoke record per run: platform, fixture ID (not a secret URL if sensitive),
extractor/browser version, cookie mode, outcome, classified reason, output duration/container probe,
and timestamp. Test public/authorised content only; never make the production worker a
credential-testing loop.
